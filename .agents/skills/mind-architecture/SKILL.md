# MIND Architecture

## Product

MIND is a Personal AI Operating System.

MIND is not a generic chatbot.

MIND must be able to:

- remember information about the user
- understand personal context
- retrieve relevant information
- manage tasks and deadlines
- organize projects
- execute multi-step work
- generate real artifacts
- proactively assist the user
- operate through Telegram
- provide a Telegram Mini App interface

The core product principle is:

"User tells MIND once. MIND remembers and acts."

---

# Architecture Principles

## 1. Modular monolith first

MIND must start as a modular monolith.

Do NOT introduce microservices unless there is a concrete technical reason.

Prefer:

- clear modules
- explicit interfaces
- isolated business logic
- reusable services

Avoid:

- premature microservices
- unnecessary abstractions
- distributed systems complexity
- duplicated logic

---

# Main modules

The backend should be conceptually divided into:

- auth
- users
- conversations
- messages
- memory
- tasks
- projects
- documents
- artifacts
- agents
- tools
- reminders
- notifications
- integrations
- billing
- observability

Modules should communicate through services/interfaces rather than directly manipulating each other's internal state.

# AI abstraction

Do not spread Gemini API calls throughout the application.

Use an AI service abstraction.

Example conceptual interface:

```ts
interface AIService {
  generate(...)
  generateStructured(...)
  embed(...)
  executeWithTools(...)
}
```

The rest of the application should not depend directly on Gemini-specific implementation details.

---

# Database rules

Every user-owned entity must contain:

```text
user_id
```

Every database query involving user data must enforce ownership.

Never trust a user_id generated by the model.

The authenticated user identity must come from the application authentication layer.

---

# Business logic

Business logic must not live inside:

* Telegram handlers
* React components
* API route handlers
* AI prompts

Business logic belongs in application/domain services.

---

# Long-running operations

Expensive operations must not block HTTP or Telegram request handlers.

Examples:

* deep research
* document generation
* presentation generation
* large file processing
* embeddings
* multi-step agent tasks

Use background jobs.

Flow:

```text
Request
→ create job
→ return acknowledgement
→ worker executes
→ persist result
→ notify user
```

---

# AI is not trusted

Never assume AI output is correct.

Validate:

* tool arguments
* IDs
* dates
* permissions
* file paths
* URLs
* generated structured data

The backend is always the final authority.

---

# Architecture changes

Before changing architecture:

1. inspect existing modules
2. inspect database schema
3. inspect existing services
4. inspect existing tools
5. inspect existing skills
6. reuse existing abstractions where appropriate

Do not create duplicate systems.

---

# Code quality

Prefer:

* simple code
* explicit types
* small modules
* deterministic behavior
* testable functions
* clear error handling

Avoid:

* giant files
* hidden global state
* magic constants
* duplicated business logic
* unnecessary design patterns

---

# Definition of done

A feature is not complete when code compiles.

It is complete when:

* implementation exists
* types are correct
* validation exists
* errors are handled
* tests exist where appropriate
* authorization is enforced
* logging exists for important operations
* behavior matches product requirements
